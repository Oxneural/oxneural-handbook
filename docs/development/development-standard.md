# Development Standard

## Project setup

Every project starts with, before the first feature commit:

- `README.md` from [`templates/PROJECT-README.md`](../../templates/PROJECT-README.md), with Classification and Status filled in
- `.gitignore` for the stack — `.env`, virtualenvs, `__pycache__`, IDE dirs, build output, data directories
- `.env.example` with placeholder values only
- Dependency file — `requirements.txt` or `pyproject.toml`, with versions pinned
- `main` branch protected

## Python

- PEP 8. Use a formatter and a linter; agree them per project and put them in CI.
- Type hints on public functions and module boundaries.
- Docstrings on anything a colleague would otherwise have to read the body to understand.
- Virtual environment per project, always. Never install into the system interpreter.
- Pin dependency versions. Unpinned dependencies make builds unreproducible and make "works on my machine" unfalsifiable.

## Structure

```
project/
├── src/ or <package>/
├── tests/
├── docs/
├── .env.example
├── requirements.txt
├── .gitignore
└── README.md
```

Separate configuration from code. Configuration comes from environment variables, never from hard-coded values or committed config files.

## Error handling

- Never silently swallow an exception. If you catch it, either handle it or re-raise it.
- Catch specific exceptions, not bare `except:`.
- Log enough context to diagnose the failure. Log no secrets, tokens or personal data.
- Validate input at the boundary — API handlers, file readers, CLI arguments. Assume input is hostile.

## Databases

- Migrations for every schema change. No manual production schema edits.
- Parameterised queries only. String-concatenated SQL is an injection vulnerability, without exception.
- Index what you filter and join on.
- Never commit a connection string.

## Testing

- Tests alongside behaviour changes, in the same pull request.
- Cover the failure paths, not only the happy path.
- Synthetic fixtures only. **Never real client data in tests**, not even anonymised.
- Tests must be runnable from a clean checkout with documented commands.

Do not publish a coverage percentage unless it is generated by a tool and reported by CI.

## Data handling

- Real client data never leaves the agreed environment, and never enters a repository.
- Generate synthetic data for development and demos.
- Delete local copies when an engagement closes.

## Documentation

Documentation ships with the change, in the same pull request. A README that describes last month's behaviour is worse than no README, because it is believed.

## Definition of done

- [ ] Works, and the failure paths are handled
- [ ] Tests written and passing
- [ ] Documentation updated
- [ ] No secrets anywhere in the diff or history
- [ ] Reviewed and approved by someone else
- [ ] Classification and Status in the README still accurate
